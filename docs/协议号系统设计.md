# 协议号系统设计（完整方案 v1.0）

> 定位：协议号 ≠ 大号。自用号是单兵作战，协议号是团队作战。
> 本系统把"一堆散号"变成"一支有分工、有调度、有替补的舰队"。

---

## 一、产品定位与信息架构

侧边栏新增折叠区「协议号系统」（专业版/企业版可见，基础版整个区隐藏），四个子页：

```
▾ 协议号系统
  ├── 舰队看板   指挥屏：全队状态一眼看清（落地页）
  ├── 协同战役   作战室：创建/监控一场战役
  ├── 角色分工   编队表：给号打角色、编组
  └── 协议号管理 装备库：现有导入/编辑/迁DC页原样挪入
```

| 子页 | 回答的问题 | 关键操作 |
|---|---|---|
| 舰队看板 | 这队号还能不能打？ | 看状态、点"发起战役" |
| 协同战役 | 这一仗打到哪了？ | 建战役、暂停/继续、看分工进度 |
| 角色分工 | 谁干什么？ | 打角色标签、编组 |
| 协议号管理 | 兵从哪来？ | 导入、编辑资料、迁DC |

设计决策：
1. 独立折叠区而非混入现有菜单——单兵/舰队两种心智分开，套餐门槛在菜单层拦截
2. 舰队看板做落地页（90% 诉求是"看一眼状态"），协议号管理沉底（低频）
3. 现有 `/sessions` 路由保留跳转（书签不失效），仅改菜单归属

## 二、角色体系（复用现有"分组管理"）

分组即编队，给分组加一个**角色类型**字段。

```sql
-- migration 033
ALTER TABLE account_groups ADD COLUMN role VARCHAR(20) NOT NULL DEFAULT '';
-- 角色取值: '' 未分配 | adder 拉人 | broadcaster 群发 | support 客服 | warmup 养号
```

- 一个组 = 一个角色（组内所有号同角色），一个号可属多个组
- 「角色分工」页 = 分组管理的增强版：每行选角色、看组内在位人数
- 战役按**角色组**选兵，而不是逐个勾选账号

## 三、协同战役（核心新增）

### 3.1 数据模型

```sql
-- migration 034
CREATE TABLE campaigns (
  id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id     UUID NOT NULL,
  name          VARCHAR(200) NOT NULL,
  status        VARCHAR(20) NOT NULL DEFAULT 'queued',
                -- queued/running/paused/completed/cancelled/failed
  objective     JSONB NOT NULL,
                -- {join_targets: ["群链接或@名",...],
                --  message: {text, media_path},
                --  join_enabled: true, send_enabled: true,
                --  send_delay: [5,12]}
  total_count   INT NOT NULL DEFAULT 0,
  done_count    INT NOT NULL DEFAULT 0,
  failed_count  INT NOT NULL DEFAULT 0,
  created_at    TIMESTAMPTZ DEFAULT NOW(),
  started_at    TIMESTAMPTZ, finished_at TIMESTAMPTZ
);
CREATE INDEX idx_campaigns_tenant ON campaigns(tenant_id, status, created_at DESC);

CREATE TABLE campaign_accounts (
  campaign_id UUID NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  account_id  UUID NOT NULL,
  role        VARCHAR(20) NOT NULL,        -- adder/broadcaster
  status      VARCHAR(20) NOT NULL DEFAULT 'active',  -- active/flood/done/replaced/dead
  assigned    INT NOT NULL DEFAULT 0,
  done        INT NOT NULL DEFAULT 0,
  failed      INT NOT NULL DEFAULT 0,
  replaced_by UUID,
  PRIMARY KEY (campaign_id, account_id)
);

CREATE TABLE campaign_targets (
  id          BIGSERIAL PRIMARY KEY,
  campaign_id UUID NOT NULL REFERENCES campaigns(id) ON DELETE CASCADE,
  target      TEXT NOT NULL,               -- 群链接/@名/群ID
  kind        VARCHAR(10) NOT NULL,        -- join / send
  status      VARCHAR(10) NOT NULL DEFAULT 'pending',  -- pending/claimed/done/failed
  account_id  UUID,                        -- 认领者
  attempts    INT NOT NULL DEFAULT 0,
  UNIQUE (campaign_id, target, kind)
);
CREATE INDEX idx_ct_pick ON campaign_targets(campaign_id, kind, status) WHERE status = 'pending';
```

### 3.2 战役引擎（internal/domain/campaign）

调度循环（每 2 秒一拍）：

```
1. 认领: UPDATE campaign_targets SET status='claimed', account_id=$acc
        WHERE id = (SELECT id FROM campaign_targets
                    WHERE campaign_id=$c AND kind=$k AND status='pending' LIMIT 1
                    FOR UPDATE SKIP LOCKED)
        每个活跃账号按"未完成数最少"优先领 1 条
2. 执行: 账号 goroutine 跑这条 (加群 或 发消息), 5-12s 随机节奏
3. 结果: done → done_count++ / failed → attempts++
        attempts>=2 判 failed, 记入 failed_count
4. 异常: FLOOD_WAIT → 账号标 flood, 它的 pending 全部释放回池, 该号冷却到限流结束
        号死了(banned/restricted) → 标 dead, 从该角色组剩余兵力自动拉替补
5. 阶段: join 阶段全部 done/failed 后 → send 阶段的 target 才变为可认领
        (send target = join 成功的那些群)
6. 收尾: 全部 done/failed → campaigns.status=completed, 发战役报告
```

关键规则：
- **绝不重复**：UNIQUE(campaign_id, target, kind) + SKIP LOCKED 认领，两个号永远不会领到同一个目标
- **互不干扰**：每个号独立节奏、独立 goroutine，一个号 FLOOD 不影响队友
- **自动替补**：dead/flood 的号的未完成任务自动回池重分配
- **尊重物理限制**：号池/传输/迁移全部复用现有 accEngine（GetClient 自带传输缓存+预热+DC迁移），不自建连接

### 3.3 战役报告（完成时生成）

```

```

```json
{
  "total": 50, "online": 41, "standby": 6, "dead": 3,
  "by_dc": {"1": 12, "2": 38},
  "by_role": {"adder": 16, "broadcaster": 20, "warmup": 8},
  "health_avg": 92,
  "today": {"joined": 320, "sent": 511, "replaced": 1},
  "active_campaigns": 2,
  "campaign_stats_7d": {"total": 9, "completed": 7}
}
```

看板 UI：顶部 4 个大数字卡 → 兵力分布（角色×状态矩阵）→ 今日战果 →
活跃战役进度条列表 → 「发起战役」主按钮（状态差时变"先补号"提示）。

## 五、API 一览（全部走协议号套餐门槛 canUseProtocol）

```
GET  /api/v1/fleet/summary                     舰队看板聚合
POST /api/v1/campaigns                         创建战役 {name, roles:{adder:groupId, broadcaster:groupId}, objective}
GET  /api/v1/campaigns?range=today|7d|all      战役列表
GET  /api/v1/campaigns/:id                     战役详情(含每号分工/进度)
POST /api/v1/campaigns/:id/pause|resume|cancel 战役控制
PUT  /api/v1/account-groups/:id/role           设置组角色 {role}
```

事件推送复用现有 SSE：`evt.type='campaign_event'`（进度/号状态/报告），前端 LiveTaskFeed 同款机制。

## 六、前端页面

**Fleet.vue（舰队看板）**：统计卡 + 分布矩阵 + 今日战果 + 活跃战役列表 + 发起战役 CTA
**Campaigns/Index.vue**：战役列表（复用任务页"今日/7日/全部"Tab 模式）+ 新建向导
- 向导三步：① 命名+粘贴目标(群链接，一行一个，自动去重) ② 消息内容(文字+媒体) ③ 选角色组(拉人组/群发组，显示各组在位人数)
**Campaigns/Detail.vue**：总进度环 + 每号一行(角色/完成/失败/状态徽章) + 暂停/继续/取消 + 实时日志
**Roles.vue**：组列表(组名/角色下拉/人数/在位状态) + 新建组

菜单改造：`globalMenuItems` 支持 `children` 折叠分组 + 按套餐隐藏（前端读 auth/me 的 plan，后端 API 仍强制校验）。

## 七、与现有系统的关系（复用清单）

| 现有能力 | 战役中怎么用 |
|---|---|
| 连接池+传输缓存+预热 | 号执行时 GetClient 直接用，零改动 |
| DC 自动迁移 | 死 DC 的号照常被救活后自动参战 |
| 内存自适应调度 | 战役并发数 = 按角色组兵力 × 内存压缩系数 |
| FLOOD 精确等待 | 单条任务级；战役级按"号冷却+任务回池"处理 |
| 日志7天清理 | campaign 三张表同样纳入 cleanupLoop |
| panic TG 告警 | 战役引擎 goroutine 全部走 safego |
| SSE 推送 | 新增 campaign_event 类型，单连接复用 |

## 八、实施阶段

**P1 骨架（小）**：菜单分组改造 + 舰队看板页 + 分组 role 字段 + Roles 页
**P2 核心（大）**：三张表 + 战役引擎 + 战役列表/详情/向导 + SSE campaign_event
**P3 增强**：养号模式（自动热身 routine）、战役报告导出 CSV、替补策略配置

P2 的引擎是最难的一块（认领并发/阶段推进/替补），其余都是熟练工。

---

## 九、明确不做的事（防止 scope 爆炸）

- 不做"战役内号独占"（v1 共享连接池，靠节奏防干扰；如实战出现互相挤占再加锁）
- 不做跨租户协同（舰队是租户私有的）
- 不做自动买号/补号对接（替补池 = 你自己导入的冷备号）
- 养号模式放 P3（先证明战役跑得起来）
