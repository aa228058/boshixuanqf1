# 前端审查技能

## 目标

对本仓库 `web/` 前端进行系统性审查，找出真实、可复现、会影响用户体验或功能的缺陷。重点覆盖桌面端和移动端，不只检查代码格式，也检查页面结构、交互状态和视觉一致性。

本项目技术栈：Vue 3、TypeScript、Vite、Vue Router、Pinia、TDesign Vue Next、Lucide Vue、Vitest。前端目录为 `web/`。

## 工作原则

1. 先理解现有实现和设计系统，再提出或实施修改。优先复用已有组件、CSS 变量、设计令牌和公共样式。
2. 不凭空重构，不为了统一而改变业务流程、API 契约、权限判断、数据结构或用户已有配置。
3. 审查与修复分开说明。用户只要求审查时，先报告问题和证据，不擅自大范围修改；用户要求修复时再实施。
4. 不把静态代码检查说成浏览器实测。没有真实运行浏览器时，明确标注视觉与交互尚未实测。
5. 每项问题尽可能提供文件路径、组件/选择器、触发条件、用户影响和建议修复方式。
6. 避免一次只修一个小问题。用户要求全面处理时，按页面和组件分组批量审查、修复及验证。
7. 不提交密钥、令牌、Cookie、环境变量或真实用户数据；不得输出 `.env` 内容。
8. 不触碰生产数据库和服务器部署。前端审查默认只读仓库；部署必须另获明确指示。

## 审查范围

### 1. 视觉系统与一致性

- 检查颜色、字体、字号、字重、行高、间距、圆角、阴影、边框、层级是否使用统一设计令牌。
- 检查主按钮、次按钮、危险按钮、文字按钮、图标按钮、输入框、下拉框、标签、卡片、表格、分页和状态提示是否一致。
- 检查相同语义的操作是否在不同页面出现不同尺寸、颜色、间距或交互反馈。
- 优先复用 `web/src/styles/ui-kit.css`、现有设计令牌及公共 UI 组件；不要另造一套平行样式。
- 查找散落的硬编码颜色、尺寸、重复 CSS 和局部覆盖，判断是否确实造成不一致后再修改。

### 2. 布局与响应式

至少分别按桌面端和移动端思考与检查：

- 页面是否横向溢出、内容被裁切、按钮挤压、表格无法操作。
- 顶栏、侧栏、底部导航、抽屉、弹窗和页面主体是否正确避让。
- 弹窗在桌面端是否居中，移动端是否符合项目既定抽屉/全屏行为。
- 弹窗最大高度、内部滚动、背景滚动锁定、遮罩点击、Esc 关闭和层级是否合理。
- 固定定位元素是否遮挡表单、底部按钮或导航。
- 长文本、长链接、空数据、大数据量和窄屏时布局是否稳定。

### 3. 交互与功能

- 检查按钮是否有正确动作、加载态、禁用态和防重复提交。
- 所有非提交按钮显式使用 `type="button"`；表单提交按钮明确使用 `type="submit"`。
- 检查是否存在按钮/链接等交互元素嵌套。
- 检查表单校验、错误提示、成功反馈、取消行为和脏数据保护。
- 检查开关、标签页、折叠项、选择框是否保留正确语义、键盘操作和状态同步。
- 检查异步请求的加载、空、成功、失败状态，以及组件卸载后的请求/事件清理。
- 不得为了修复样式而移除开关、标签页、菜单等控件的语义或业务行为。

### 4. 可访问性

- 图标按钮应有明确的 `aria-label` 或可访问名称。
- 菜单、弹窗、导航、标签页、开关应有适当的角色、状态和关联属性。
- 检查键盘可达性、焦点可见性、弹窗焦点管理、颜色对比和表单标签。
- 避免仅依赖颜色表达成功、失败、警告或选中状态。
- 不要用非交互元素模拟按钮；不要给普通按钮随意添加错误的 ARIA role。

### 5. Vue 与代码质量

- 检查 Vue 模板结构、组件边界、重复逻辑、错误的 key、响应式状态使用和事件监听清理。
- 检查控制台错误风险、未处理 Promise、竞态条件、空值访问和不必要的重复请求。
- 检查路由切换、页面卸载、弹窗打开关闭时的状态与资源清理。
- 检查 TypeScript 类型是否准确，避免用 `any` 掩盖问题。
- 关注大列表渲染、频繁计算和不必要的组件更新，但避免无证据的过度优化。

### 6. 安全与数据呈现

- 检查用户输入、富文本、动态 HTML 和 URL 的安全处理。
- 检查敏感信息是否可能出现在页面、日志或错误提示中。
- 检查危险操作是否有明确确认、结果反馈及权限保护。
- 检查群组、任务、消息、账号等业务数据的空值、异常值和超长内容呈现。

## 执行流程

1. **确认基线**：读取仓库当前分支和最新提交，查看 `web/package.json`、路由、全局样式、设计令牌、公共组件和测试配置。
2. **建立清单**：枚举 `web/src/views`、`web/src/components`、`web/src/styles` 中的页面、组件和样式文件；按业务模块分组，不漏掉管理端、验证端、移动端布局。
3. **全局扫描**：搜索未声明 type 的按钮、嵌套交互元素、缺少可访问名称的图标按钮、重复/硬编码样式、危险的弹窗层级和横向溢出风险。
4. **逐页审查**：结合组件调用关系和公共样式检查页面，不以搜索命中数量代替人工判断；识别共性问题和单页问题。
5. **分级记录**：使用以下级别：
   - P0：安全、数据丢失、核心功能不可用。
   - P1：核心流程错误、严重布局/交互故障、移动端无法完成关键操作。
   - P2：明显视觉不一致、可访问性缺陷、常见场景下的交互问题。
   - P3：轻微样式瑕疵、低风险维护性问题。
6. **修复策略**：先修公共组件/设计令牌层面的根因，再修页面特例；控制改动范围，保持现有业务语义。
7. **验证**：在 `web/` 目录按可用脚本执行：
   - `npm run typecheck`
   - `npm run test -- --run`（若脚本参数不兼容则使用 `npm run test`）
   - `npm run check:design-tokens`
   - `npm run build`
   先确认依赖安装和脚本存在。逐项记录通过、失败或未执行，不得伪造结果。
8. **复核**：检查 diff，确认没有意外业务逻辑变更、无障碍退化、重复样式或引入新依赖；总结仍未验证的浏览器场景。

## 问题报告格式

每个问题按以下格式记录：

- **级别**：P0/P1/P2/P3
- **位置**：文件路径及组件/代码位置
- **现象**：当前实际行为
- **复现条件**：在哪个页面、设备宽度或操作步骤下出现
- **影响**：对用户或业务流程的影响
- **建议/修复**：根因和最小安全改法
- **验证**：测试或复核结果

最终总结必须包含：

1. 审查覆盖范围及未覆盖部分。
2. 按 P0-P3 汇总的问题数量。
3. 已修复内容与对应文件。
4. 执行过的检查命令及真实结果。
5. 尚未解决或需要真实浏览器/设备验证的事项。
6. 是否提交 Git、提交 SHA；没有提交就明确说明。
7. 是否部署；未经明确部署且验证不得声称已部署。

## 完成标准

- 关键页面、公共组件、桌面端和移动端均纳入审查范围，未覆盖项有明确说明。
- 共性问题优先从公共样式/组件解决，避免每页重复打补丁。
- 不破坏既有功能、接口、权限和业务数据。
- 结论有代码证据和验证结果支撑，不用“看起来没问题”代替验证。
