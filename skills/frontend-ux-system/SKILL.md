# tg-sender 前端 UX/UI 统一工作流

本技能是本仓库专用的编排层，将商业后台 UX、复杂企业流程、组件实现规范、系统性 UX 审查和视觉精修整合为一套有先后顺序的流程。它不是把多个通用技能机械叠加，也不替代项目已有的开发和审查技能。

## 1. 权威顺序与项目事实

发生规则冲突时，按以下顺序裁决：

1. 用户本次明确要求及已确认的产品行为。
2. 当前仓库代码、真实运行行为、现有 API 契约和测试。
3. `skills/frontend-dev/SKILL.md` 中的项目技术约束。
4. `skills/frontend-review/SKILL.md` 中的审查要求。
5. 本技能中的 UX/UI 工作流。
6. 通用设计经验。

**项目现有技术栈不是 Element Plus。** 当前前端基线为 Vue 3、TypeScript、Vite、Pinia、TDesign Vue Next、Lucide Vue、Vue Final Modal、Tailwind CSS 4 等，具体以 `web/package.json` 和实际代码为准。不得因为引入或参考了 `element-plus-patterns` 就安装 Element Plus、复制其组件标签/API/类名，或建立第二套 UI 体系。

从 Element Plus 业务模式中只吸收与组件库无关的设计思想，例如表单校验、表格状态、筛选、批量操作、分页、弹窗确认、加载反馈和错误恢复；实现时必须映射到仓库现有 TDesign 组件及项目封装。

## 2. 技能职责分工

| 能力来源 | 在本项目中的职责 | 不负责 |
|---|---|---|
| frontend-dev | 代码、架构、技术栈、组件和 API 的项目事实 | 单独决定产品 UX |
| element-plus-patterns（模式参考） | 提供常见 B2B 控件/业务流模式的参考 | 引入 Element Plus 或替换 TDesign |
| commercial-ui-ux（设计方法参考） | SaaS 页面信息架构、任务模式、UX→UI→GUI、商业界面质量门禁 | 覆盖项目约束或业务语义 |
| enterprise-system-ux-expert（专项方法参考） | 角色、权限、跨步骤流程、运营工作台和 KPI 语义审查 | 对每个普通页面强制套复杂 ERP 流程 |
| UI/UX Pro Max（审查方法参考） | 无障碍、响应式、触控、性能、状态完整性等系统审查 | 无证据地推翻设计系统 |
| premium-ui-polish（精修方法参考） | 视觉层级、排版、间距、边框、阴影和微交互收尾 | 在 UX 问题未解决前先做装饰 |

以上外部技能在本仓库中按用户提供的能力描述进行方法整合；若未提供其原始技能文件，不得声称已经安装、读取或完整复制其全部规则文档。

## 3. 任务模式识别：先判断问题类型

开始设计或修改前，将任务归入一个或多个模式：

- **数据浏览**：仪表盘、列表、搜索、筛选、排序、分页、详情。
- **数据录入**：创建/编辑表单、导入、批量导入、字段校验。
- **批量操作**：批量选择、批量执行、进度、部分成功、失败重试。
- **任务执行**：创建任务、配置、预览、确认、运行、暂停、恢复、结束。
- **监控与处置**：状态、告警、异常、日志、人工介入和恢复。
- **账号与权限**：账号状态、授权范围、角色、权限和敏感操作。
- **系统配置**：配置项、保存、校验、回滚和影响说明。

识别主要用户、目标、触发频率、数据规模、失败代价和完成条件。不要只根据页面名称推断流程。

## 4. UX → UI → GUI 的交付顺序

### A. UX：先保证任务可完成

1. 明确角色和权限边界；不同角色只展示其有权且需要执行的操作。
2. 明确用户进入页面的目标、前置条件、主路径、分支和结束状态。
3. 减少不必要步骤，但不得隐藏关键风险、权限或确认。
4. 明确加载、空数据、错误、部分成功、超时、取消、重试和恢复状态。
5. 大数据量操作必须设计可追踪的异步进度和结果入口，不能只依赖一个会消失的弹窗。
6. 危险或不可逆操作必须说明影响范围，并在适当位置二次确认。
7. KPI 必须定义统计对象、时间范围、单位、刷新频率和状态口径；不得只追求视觉效果而创造误导指标。

### B. UI：使用现有设计系统表达

1. 先查设计令牌、公共组件、主题、全局 CSS 导入顺序和相邻页面。
2. 页面按任务优先级组织：主要任务和关键状态优先，低频辅助信息后置。
3. 复用现有 TDesign 和项目 UI 封装；相同语义控件保持尺寸、状态、间距和反馈一致。
4. 主题必须兼容项目当前所有主题状态；不硬编码破坏主题的颜色。
5. 视觉层级服务于信息层级，不用大量卡片、渐变、阴影或装饰图标制造噪音。

### C. GUI：验证真实交互与设备表现

检查桌面端和移动端实际布局；覆盖键盘焦点、弹窗定位、滚动、遮罩、Esc、触控尺寸、长文本、固定区域遮挡和横向溢出。静态代码推断必须标注为推断，不能冒充浏览器实测。

## 5. 复杂业务专项：角色与流程

仅在涉及多角色、多阶段、批量任务或高失败代价流程时启用深度审查。

### 角色视角
- 管理员：全局配置、授权、审计、风险和异常处置。
- 运营人员：日常任务效率、批量操作、进度跟踪、失败处理。
- 普通使用者：清晰的任务入口、可理解的状态、可预测的结果。
- 系统/自动化：异步状态变化、重试、超时、幂等和可观测性。

以上为审查视角，不代表仓库必然存在这些角色；必须以实际权限模型为准。

### 关键业务流检查
- **群组库导入**：文件选择 → 解析 → 链接规范化/去重 → 筛选 → 导入队列 → 进度 → 结果统计 → 失败项查看/重试。关闭对话框后仍应能从稳定入口查看任务进度和历史结果（若业务已支持或本次需求明确要求）。
- **群发任务**：目标选择 → 内容/媒体配置 → 规则校验 → 预览/确认 → 执行 → 实时状态 → 失败明细/恢复。不得绕过后端频率限制、账号状态、权限或风险控制。
- **账号管理**：账号状态、连接状态、授权范围、异常原因和可执行操作必须区分，避免把“在线”“可用”“可发送”等不同状态混为一谈。
- **监控与验证**：指标应有口径和时间范围；异常状态应提供可执行的下一步，而非只显示颜色或数字。

业务流中的步骤名称是审查参考，不得假设每一步当前均已实现；先检查代码和 API。

## 6. 组件模式规范（不绑定 Element Plus）

### 表单
- 标签、必填标识、字段说明和校验规则清晰。
- 区分字段级错误与整体提交错误；错误信息指出如何修复。
- 提交中禁用重复提交；取消/关闭时保护未保存输入。
- 长表单分组并保留合理的信息顺序。

### 表格与数据列表
- 定义加载、空、错误、无搜索结果、分页和数据刷新状态。
- 列优先级适配桌面与窄屏；避免所有字段都挤在一行。
- 行操作有明确语义；批量操作显示选中数量和影响范围。
- 大数据量优先考虑服务端分页/筛选及现有性能方案，不在前端无界渲染。

### 弹窗、抽屉和确认
- 桌面端遵循项目规则居中；移动端遵循项目既定抽屉/全屏策略。
- 限制最大高度，内容区内部滚动，操作区清晰且不被遮挡。
- 明确关闭、取消、保存成功和失败行为；处理焦点管理、Esc、遮罩点击和滚动锁定。
- 不把所有流程塞进弹窗；长时间任务必须有持久化的进度/结果入口。

### 状态与反馈
- 状态不能只靠颜色表达；同时提供文字或图标语义。
- 区分处理中、排队中、成功、部分成功、失败、已取消和未知状态。
- Toast 用于短反馈，不替代持久任务记录、错误详情或恢复入口。

## 7. 质量门禁（提交前逐项核对）

### P0：发布阻断 / 数据与安全事故级
满足任一项即为 P0，必须停止发布/合并，优先修复并补回归测试：
- 已确认存在数据泄露、越权访问、认证绕过、敏感信息暴露或安全边界失效。
- 造成不可逆数据丢失、跨租户数据污染、批量误操作，或重复执行产生严重业务损害。
- 生产环境核心功能整体不可用，且没有安全可行的绕过路径。
- 修改引入可稳定复现的远程代码执行、注入、凭证泄露等严重安全风险。

### P1：核心功能/关键任务阻断
不一定构成安全事故，但会阻止重要用户完成关键任务；必须在本次修复范围解决，或明确回滚/禁用受影响功能：
- 核心流程无法完成，例如导入无法提交、群发任务无法启动/停止、账号无法正常连接或管理。
- 关键异步任务无进度、结果或恢复入口，可能导致用户误判任务状态或重复操作。
- 关键操作在目标设备上被遮挡、无法点击/键盘操作，且没有可用替代路径。
- 关键状态、权限或操作影响展示错误，足以诱发错误决策。
- 回归导致 API 契约、任务状态机或已有业务规则被破坏。

### P2：明显体验缺陷 / 应修复
核心任务仍可完成，但体验、可访问性、一致性或边界状态明显不足：
- 同语义按钮、表格、表单、弹窗的尺寸/行为/反馈不一致。
- 弹窗偏移、滚动区域错误、焦点管理不佳，但仍存在可用操作路径。
- 缺少加载、空、错误、部分成功、无搜索结果等状态。
- 重要图标按钮无可访问名称、焦点不可见、对比度不足。
- 主题切换、窄屏、长文本或大数据量场景出现明显布局/性能问题。

### P3：轻微视觉瑕疵 / 可排期
不影响任务发现、理解、完成、数据正确性或安全性的低影响问题：
- 按钮圆角、阴影、边框色、字距或图标基线存在轻微差异。
- 非关键装饰、动画节奏或细微间距不一致。
- 低频页面的非阻断性视觉细节。

**分级边界示例：** 单纯“按钮圆角不一致”通常是 P3；若按钮尺寸差异导致关键操作在移动端无法点击，则升为 P1。弹窗不在视觉中心但内容和操作仍可用通常是 P2；若关键确认按钮被遮挡导致任务无法完成，则为 P1。不能仅凭问题所在组件或视觉显眼程度定级，必须按影响范围、可复现性、任务阻断程度、数据/安全后果定级。

质量检查维度：
1. 任务可发现性与完成效率。
2. 信息架构与视觉层级。
3. 控件一致性与交互反馈。
4. 表单/表格/弹窗完整状态。
5. 键盘、焦点、语义和对比度。
6. 桌面/移动响应式和触控。
7. 大数据量性能与异步任务可观测性。
8. 主题一致性和视觉细节。
9. 权限、危险操作和数据安全。
10. 回归风险、测试覆盖和维护成本。

## 7A. 冲突裁决矩阵（必须按此执行）

| 冲突情形 | 裁决规则 | 执行方式 |
|---|---|---|
| UI/UX Pro Max 建议与 TDesign 组件现有行为冲突 | 项目现有组件/API 和已确认产品行为优先；UX 建议是审查依据，不是强制替换指令 | 优先通过 TDesign 官方 props、slots、事件和项目封装实现；若组件行为确实造成 P1/P2 问题，先验证可配置方案，再考虑项目级封装或替换组件，并补测试 |
| commercial-ui-ux 布局建议与 frontend-dev 目录/架构约束冲突 | frontend-dev 的项目架构约束优先，commercial-ui-ux 只决定信息架构与交互目标 | 在既有路由、页面目录、组件边界内调整布局；不得为了套用示例重组目录或引入新框架 |
| enterprise-system-ux-expert 建议增加角色/步骤，但仓库没有对应权限或状态模型 | 真实权限模型、API 和后端状态机优先 | 不虚构角色、审批、状态或 KPI；先列为产品缺口，不在纯 UI 修改中伪造 |
| element-plus-patterns 示例与 TDesign API 不同 | 只迁移无关组件库的交互模式，不迁移标签、props、事件、CSS 类名 | 用 TDesign 现有组件或项目封装实现；无法映射时说明差异并设计适配层，不安装 Element Plus |
| premium-ui-polish 的视觉建议与可访问性/可读性冲突 | 可访问性、可读性和状态辨识优先于装饰效果 | 不降低对比度、不移除 focus、不用颜色作为唯一状态编码；必要时放弃视觉效果 |
| 设计 token 规则与第三方组件必需样式冲突 | 项目 token 约束优先，但允许通过集中式主题桥接/覆盖适配第三方组件 | 不在页面散落硬编码；把例外放到统一主题层并写明原因、范围和验证方式 |
| 用户本次明确要求与一般设计建议冲突 | 用户明确要求优先，但不得违反安全、数据正确性和已确认的不可变业务约束 | 如会改变业务行为或产生风险，先说明影响；不得默默改变产品语义 |

**裁决步骤：** 记录冲突双方的具体建议与代码/文档证据 → 判断是否涉及安全、业务契约或架构边界 → 按上表选优先级 → 选择影响最小的实现 → 添加针对性测试 → 在交付报告中记录取舍。不得用“某技能更专业”作为推翻仓库事实的理由。

## 7B. 代码级禁止项与正确示例

以下示例是本项目的硬约束。示例中的 TDesign 组件必须以当前全局注册和实际组件 API 为准。

### 禁止引入 Element Plus

```vue
<!-- ❌ 错误：项目没有 Element Plus 组件体系 -->
<el-button type="primary">保存</el-button>
```

```ts
// ❌ 错误：不得新增 Element Plus 依赖或全局安装
import ElementPlus from 'element-plus'
import 'element-plus/dist/index.css'
app.use(ElementPlus)
```

```vue
<!-- ✅ 正确：使用项目已注册的 TDesign 组件 -->
<t-button theme="primary">保存</t-button>
```

```ts
// ✅ 正确：项目入口已统一引入 TDesign 样式并按需注册组件
import 'tdesign-vue-next/es/style/index.css'
import { Button } from 'tdesign-vue-next'
app.use(Button)
```

### 禁止在页面建立平行样式体系

```css
/* ❌ 错误：页面散落颜色、阴影、圆角和间距常量 */
.panel { color: #333; border-radius: 13px; box-shadow: 0 4px 12px #0002; padding: 17px; }
```

```css
/* ✅ 正确：优先使用 web/src/styles/tokens.css 中已有语义令牌 */
.panel {
  color: var(--t-text-1);
  border-radius: var(--t-radius-md);
  box-shadow: var(--t-shadow-sm);
  padding: var(--t-space-4);
}
```

### 禁止绕过现有组件封装

```vue
<!-- ❌ 错误：同一语义按钮在页面自行拼装，产生第二套行为/样式 -->
<button class="my-new-primary-button" @click="save">保存</button>
```

```vue
<!-- ✅ 正确：优先复用项目统一按钮组件；若仓库该页面规范要求 TDesign，则使用 t-button -->
<t-button theme="primary" :loading="saving" @click="save">保存</t-button>
```

原生 button 并非绝对禁止：仅用于项目封装、语义上不是 TDesign 控件，或 TDesign 无法满足的原生交互；必须保留键盘、焦点、禁用和可访问名称。

## 9A. 最小可操作验收标准

### 命令级验收

以 `web/package.json` 当前 scripts 为准，当前仓库定义了：
- `npm run typecheck`：退出码必须为 0；不得有 TypeScript/Vue 类型错误。
- `npm run test`：退出码必须为 0；本次修改涉及的测试必须执行，不能用跳过测试掩盖失败。
- `npm run build`：退出码必须为 0；不得有编译错误。既有非阻断 warning 需记录，不得把 warning 描述为 error。
- `npm run check:design-tokens`：退出码必须为 0；扫描范围内违规数必须为 **0**，没有“允许 1–2 个误差”的豁免。

### Design token 检查器的真实规则与范围

当前 `web/scripts/check-design-tokens.mjs` 对传入/选中的 Vue 文件执行以下硬检查：
1. 禁止 legacy palette utility：包括 cyan、amber、rose、emerald、green、red、orange 等旧色板类名；改用语义 token/项目约定类。
2. Vue `<style>` 块中禁止硬编码颜色字面量（hex、rgb/rgba、hsl/hsla）。
3. Vue `<style>` 块中禁止硬编码 `box-shadow`（允许 `none` 或 `var(...)`）。
4. Vue `<style>` 块中禁止硬编码 `border-radius`（允许 `0` 或 `var(...)`）。
5. Vue `<style>` 块中禁止硬编码 `font-size`（允许 `0` 或 `var(...)`）。
6. Vue `<style>` 块中 `padding`、`margin`、`gap` 及其方向属性禁止直接写 px/rem/em/vw/vh/% 数值；应使用 token。检查器会先剥离简单的 `var(...)`、`calc(...)`、`env(...)` 表达式。

**扫描范围注意：** 不传文件参数时，脚本通过 `git diff --name-only HEAD^ HEAD -- web/src` 只选择最近一次提交中变更的 Vue 文件，并非全站扫描；显式传入文件路径可扩大本次扫描范围。全站审查或大规模样式重构时，必须显式传入所有相关 Vue 文件，或另行运行全量检查方案。不得把“最近提交文件通过”表述成“全站 token 零违规”。该脚本当前不检查所有全局 CSS 文件，也不验证视觉对比度或 token 数值是否设计合理，这些需另行审查。

### 代码与交互验收清单

- [ ] 使用的组件、props、事件、slot 与当前 TDesign Vue Next 版本/API 一致；无未注册组件。
- [ ] 没有新增 Element Plus、第二套 UI 库、CSS 框架或图标库。
- [ ] 颜色、字体、阴影、圆角、间距优先使用现有语义 token；例外集中管理并说明原因。
- [ ] 表单具备校验、提交中防重复提交、成功/失败反馈和未保存状态处理。
- [ ] 列表/表格具备加载、空、错误、无结果、分页/刷新状态；批量操作说明影响范围。
- [ ] 弹窗桌面端居中，内容区滚动、操作区可见；Esc/关闭/焦点/滚动锁定行为符合项目约定。
- [ ] 异步任务有稳定进度与结果入口；关闭弹窗不会丢失用户查看任务状态的路径。
- [ ] 桌面和移动关键视口无横向溢出、遮挡或不可点击控件；键盘可完成关键操作。
- [ ] 状态不只靠颜色表达；图标按钮有可访问名称，焦点状态清晰。
- [ ] 业务 API、权限、任务状态机和后端规则未被视觉重构擅自改变。

**通过定义：** 所有适用的必选项完成；命令退出码为 0；相关测试通过；未执行的浏览器/设备测试明确标为“未验证”；任何豁免都必须列出文件、规则、原因、影响和后续处理，不得静默忽略。

## 8. 视觉精修的最后顺序

只有 UX 路径和组件行为稳定后，才进行 polish。依次检查：
1. 字体层级、字号、字重、行高和数字对齐。
2. 间距节奏、容器宽度、对齐线和留白。
3. 边框、分隔线、圆角和阴影层次。
4. 图标尺寸、基线、按钮内部间距。
5. hover、focus、active、disabled、loading 等微交互。
6. 空状态、成功/错误/警告反馈的视觉表达。

不允许为了“高级感”引入新的 CSS 框架、组件库、图标库或大量局部特例。

## 9. 执行与验证协议

1. 先读取 `skills/frontend-dev/SKILL.md` 和 `skills/frontend-review/SKILL.md`，再读取当前页面、调用方、路由、API、样式和测试。
2. 识别任务模式、用户角色、主路径、异常分支和验收条件。
3. 先修公共根因，再修页面特例；一次性覆盖同一问题的全部调用点。
4. 对复杂业务先画清状态流/步骤流，再修改代码。
5. 实施后检查 diff、重复 CSS、重复属性、无用 import、业务语义和权限回归。
6. 按仓库当前可用脚本执行：`npm run typecheck`、`npm run test`、`npm run check:design-tokens`、`npm run build`；先核对 package scripts，不得假设命令存在。
7. 若可用真实浏览器/设备，验证关键视口和交互；否则明确列为未实测。
8. 报告修改范围、根因、测试结果、未验证项、提交 SHA 和部署状态。不得声称未执行的检查已通过。

## 10. 防止技能冲突的简明规则

- 项目事实优先于通用模式；TDesign 项目不套用 Element Plus API。
- UX 先于视觉 polish；可用性先于装饰。
- 复杂流程技能只审查确有复杂度的流程，不给普通 CRUD 页面增加不必要步骤。
- 审查清单用于发现风险，不是要求每页机械满足所有条目。
- 发现设计系统根因时优先修公共 token/组件；不得创建平行设计系统。
- 用户只要求审查时先交付证据和分级清单；用户要求修复时再实施。
- 不改变业务逻辑来满足视觉规则；必要的产品行为变更先明确说明并取得用户要求。
