# tg-sender 前端 UX/UI 统一工作流

本技能是本仓库专用的编排层，将商业后台 UX、复杂企业流程、组件实现规范、系统性 UX 审查和视觉精修整合为一套有先后顺序的流程。它不是把多个通用技能机械叠加，也不替代项目已有的开发和审查技能。

## 1. 权威顺序与项目事实

发生规则冲突时，按以下顺序裁决：

1. 用户本次明确要求及已确认的产品行为。
2. 当前仓库代码、真实运行行为、现有 API 契约和测试。
3. `skills/frontend-dev/SKILL.md` 中的项目技术约束。
4. `skills/frontend-review/SKILL.md` 中的审查要求。
5. 本技能中的 UX/UI 工作流。
6. 通用设计经验。

**项目现有技术栈不是 Element Plus。** 当前前端基线为 Vue 3、TypeScript、Vite、Pinia、TDesign Vue Next、Lucide Vue、Vue Final Modal、Tailwind CSS 4 等，具体以 `web/package.json` 和实际代码为准。不得因为引入或参考了 `element-plus-patterns` 就安装 Element Plus、复制其组件标签/API/类名，或建立第二套 UI 体系。

从 Element Plus 业务模式中只吸收与组件库无关的设计思想，例如表单校验、表格状态、筛选、批量操作、分页、弹窗确认、加载反馈和错误恢复；实现时必须映射到仓库现有 TDesign 组件及项目封装。

## 2. 技能职责分工

| 能力来源 | 在本项目中的职责 | 不负责 |
|---|---|---|
| frontend-dev | 代码、架构、技术栈、组件和 API 的项目事实 | 单独决定产品 UX |
| element-plus-patterns（模式参考） | 提供常见 B2B 控件/业务流模式的参考 | 引入 Element Plus 或替换 TDesign |
| commercial-ui-ux（设计方法参考） | SaaS 页面信息架构、任务模式、UX→UI→GUI、商业界面质量门禁 | 覆盖项目约束或业务语义 |
| enterprise-system-ux-expert（专项方法参考） | 角色、权限、跨步骤流程、运营工作台和 KPI 语义审查 | 对每个普通页面强制套复杂 ERP 流程 |
| UI/UX Pro Max（审查方法参考） | 无障碍、响应式、触控、性能、状态完整性等系统审查 | 无证据地推翻设计系统 |
| premium-ui-polish（精修方法参考） | 视觉层级、排版、间距、边框、阴影和微交互收尾 | 在 UX 问题未解决前先做装饰 |

以上外部技能在本仓库中按用户提供的能力描述进行方法整合；若未提供其原始技能文件，不得声称已经安装、读取或完整复制其全部规则文档。

## 3. 任务模式识别：先判断问题类型

开始设计或修改前，将任务归入一个或多个模式：

- **数据浏览**：仪表盘、列表、搜索、筛选、排序、分页、详情。
- **数据录入**：创建/编辑表单、导入、批量导入、字段校验。
- **批量操作**：批量选择、批量执行、进度、部分成功、失败重试。
- **任务执行**：创建任务、配置、预览、确认、运行、暂停、恢复、结束。
- **监控与处置**：状态、告警、异常、日志、人工介入和恢复。
- **账号与权限**：账号状态、授权范围、角色、权限和敏感操作。
- **系统配置**：配置项、保存、校验、回滚和影响说明。

识别主要用户、目标、触发频率、数据规模、失败代价和完成条件。不要只根据页面名称推断流程。

## 4. UX → UI → GUI 的交付顺序

### A. UX：先保证任务可完成

1. 明确角色和权限边界；不同角色只展示其有权且需要执行的操作。
2. 明确用户进入页面的目标、前置条件、主路径、分支和结束状态。
3. 减少不必要步骤，但不得隐藏关键风险、权限或确认。
4. 明确加载、空数据、错误、部分成功、超时、取消、重试和恢复状态。
5. 大数据量操作必须设计可追踪的异步进度和结果入口，不能只依赖一个会消失的弹窗。
6. 危险或不可逆操作必须说明影响范围，并在适当位置二次确认。
7. KPI 必须定义统计对象、时间范围、单位、刷新频率和状态口径；不得只追求视觉效果而创造误导指标。

### B. UI：使用现有设计系统表达

1. 先查设计令牌、公共组件、主题、全局 CSS 导入顺序和相邻页面。
2. 页面按任务优先级组织：主要任务和关键状态优先，低频辅助信息后置。
3. 复用现有 TDesign 和项目 UI 封装；相同语义控件保持尺寸、状态、间距和反馈一致。
4. 主题必须兼容项目当前所有主题状态；不硬编码破坏主题的颜色。
5. 视觉层级服务于信息层级，不用大量卡片、渐变、阴影或装饰图标制造噪音。

### C. GUI：验证真实交互与设备表现

检查桌面端和移动端实际布局；覆盖键盘焦点、弹窗定位、滚动、遮罩、Esc、触控尺寸、长文本、固定区域遮挡和横向溢出。静态代码推断必须标注为推断，不能冒充浏览器实测。

## 5. 复杂业务专项：角色与流程

仅在涉及多角色、多阶段、批量任务或高失败代价流程时启用深度审查。

### 角色视角
- 管理员：全局配置、授权、审计、风险和异常处置。
- 运营人员：日常任务效率、批量操作、进度跟踪、失败处理。
- 普通使用者：清晰的任务入口、可理解的状态、可预测的结果。
- 系统/自动化：异步状态变化、重试、超时、幂等和可观测性。

以上为审查视角，不代表仓库必然存在这些角色；必须以实际权限模型为准。

### 关键业务流检查
- **群组库导入**：文件选择 → 解析 → 链接规范化/去重 → 筛选 → 导入队列 → 进度 → 结果统计 → 失败项查看/重试。关闭对话框后仍应能从稳定入口查看任务进度和历史结果（若业务已支持或本次需求明确要求）。
- **群发任务**：目标选择 → 内容/媒体配置 → 规则校验 → 预览/确认 → 执行 → 实时状态 → 失败明细/恢复。不得绕过后端频率限制、账号状态、权限或风险控制。
- **账号管理**：账号状态、连接状态、授权范围、异常原因和可执行操作必须区分，避免把“在线”“可用”“可发送”等不同状态混为一谈。
- **监控与验证**：指标应有口径和时间范围；异常状态应提供可执行的下一步，而非只显示颜色或数字。

业务流中的步骤名称是审查参考，不得假设每一步当前均已实现；先检查代码和 API。

## 6. 组件模式规范（不绑定 Element Plus）

### 表单
- 标签、必填标识、字段说明和校验规则清晰。
- 区分字段级错误与整体提交错误；错误信息指出如何修复。
- 提交中禁用重复提交；取消/关闭时保护未保存输入。
- 长表单分组并保留合理的信息顺序。

### 表格与数据列表
- 定义加载、空、错误、无搜索结果、分页和数据刷新状态。
- 列优先级适配桌面与窄屏；避免所有字段都挤在一行。
- 行操作有明确语义；批量操作显示选中数量和影响范围。
- 大数据量优先考虑服务端分页/筛选及现有性能方案，不在前端无界渲染。

### 弹窗、抽屉和确认
- 桌面端遵循项目规则居中；移动端遵循项目既定抽屉/全屏策略。
- 限制最大高度，内容区内部滚动，操作区清晰且不被遮挡。
- 明确关闭、取消、保存成功和失败行为；处理焦点管理、Esc、遮罩点击和滚动锁定。
- 不把所有流程塞进弹窗；长时间任务必须有持久化的进度/结果入口。

### 状态与反馈
- 状态不能只靠颜色表达；同时提供文字或图标语义。
- 区分处理中、排队中、成功、部分成功、失败、已取消和未知状态。
- Toast 用于短反馈，不替代持久任务记录、错误详情或恢复入口。

## 7. 质量门禁（提交前逐项核对）

### P0 / P1：必须阻断
- 核心业务路径不可完成、数据丢失/重复提交、权限或安全边界被破坏。
- UI 修改改变 API 契约、任务语义、账号限制或后端业务规则。
- 关键操作没有明确结果，或异步任务失去追踪能力。
- 桌面/移动端关键操作被遮挡、无法点击或无法键盘操作。

### P2：应修复
- 同语义控件样式/行为不一致。
- 表单、表格、弹窗缺少常见状态。
- 重要图标按钮无可访问名称、焦点不可见、对比度不足。
- 主题切换、窄屏、长文本或高数据量场景明显异常。

### P3：可排期
- 不影响任务完成的轻微视觉瑕疵。
- 非关键动画、阴影、圆角、字距和装饰细节。

质量检查维度：
1. 任务可发现性与完成效率。
2. 信息架构与视觉层级。
3. 控件一致性与交互反馈。
4. 表单/表格/弹窗完整状态。
5. 键盘、焦点、语义和对比度。
6. 桌面/移动响应式和触控。
7. 大数据量性能与异步任务可观测性。
8. 主题一致性和视觉细节。
9. 权限、危险操作和数据安全。
10. 回归风险、测试覆盖和维护成本。

## 8. 视觉精修的最后顺序

只有 UX 路径和组件行为稳定后，才进行 polish。依次检查：
1. 字体层级、字号、字重、行高和数字对齐。
2. 间距节奏、容器宽度、对齐线和留白。
3. 边框、分隔线、圆角和阴影层次。
4. 图标尺寸、基线、按钮内部间距。
5. hover、focus、active、disabled、loading 等微交互。
6. 空状态、成功/错误/警告反馈的视觉表达。

不允许为了“高级感”引入新的 CSS 框架、组件库、图标库或大量局部特例。

## 9. 执行与验证协议

1. 先读取 `skills/frontend-dev/SKILL.md` 和 `skills/frontend-review/SKILL.md`，再读取当前页面、调用方、路由、API、样式和测试。
2. 识别任务模式、用户角色、主路径、异常分支和验收条件。
3. 先修公共根因，再修页面特例；一次性覆盖同一问题的全部调用点。
4. 对复杂业务先画清状态流/步骤流，再修改代码。
5. 实施后检查 diff、重复 CSS、重复属性、无用 import、业务语义和权限回归。
6. 按仓库当前可用脚本执行：`npm run typecheck`、`npm run test`、`npm run check:design-tokens`、`npm run build`；先核对 package scripts，不得假设命令存在。
7. 若可用真实浏览器/设备，验证关键视口和交互；否则明确列为未实测。
8. 报告修改范围、根因、测试结果、未验证项、提交 SHA 和部署状态。不得声称未执行的检查已通过。

## 10. 防止技能冲突的简明规则

- 项目事实优先于通用模式；TDesign 项目不套用 Element Plus API。
- UX 先于视觉 polish；可用性先于装饰。
- 复杂流程技能只审查确有复杂度的流程，不给普通 CRUD 页面增加不必要步骤。
- 审查清单用于发现风险，不是要求每页机械满足所有条目。
- 发现设计系统根因时优先修公共 token/组件；不得创建平行设计系统。
- 用户只要求审查时先交付证据和分级清单；用户要求修复时再实施。
- 不改变业务逻辑来满足视觉规则；必要的产品行为变更先明确说明并取得用户要求。
