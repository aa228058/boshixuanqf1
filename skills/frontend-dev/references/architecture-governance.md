# 前端架构与样式治理规范

> 适用范围：`web/`。本文件定义职责边界和迁移规则，不代表历史代码已完成迁移。

## 1. 目标

减少同一职责的平行实现，降低全局 CSS 层叠复杂度。遵循“一个职责一个主入口；旧实现可暂时兼容，但禁止继续扩张”。

不以减少文件数量或依赖数量作为唯一目标。只有确认无调用、无动态引用、无插件/构建用途后，才能删除代码或依赖。

## 2. 已确认的仓库基线

以当前 `main` 为准：

- Vue 3、TypeScript、Vite
- Pinia、Vue Router
- TDesign Vue Next（按需注册）
- vue-final-modal、vue-sonner
- lucide-vue-next
- Tailwind CSS 4
- Vitest、vue-tsc

入口：`web/src/main.ts`；依赖：`web/package.json`。

## 3. 职责边界（目标态）

| 职责 | 主实现 | 边界 |
|---|---|---|
| 基础交互控件 | TDesign Vue Next | Button、Input、Select、Table、Dialog 等基础控件优先使用已注册组件 |
| 项目业务组件 | `src/components/ui/` 等项目组件 | 只封装项目特有交互、业务语义或基础库无法满足的体验；不得复制一套通用控件库 |
| 布局与响应式 | Tailwind CSS | 页面结构、flex/grid、间距、断点；不承载另一套组件视觉主题 |
| 设计变量 | `styles/tokens.css` | 颜色、字号、间距、圆角、阴影、层级等语义 token 的唯一源头 |
| 组件局部样式 | Vue scoped CSS | 只影响当前组件；不得重复定义全局通用控件 |
| 全局基础样式 | `styles/` 中受控文件 | Reset、主题变量、第三方库必要覆盖、全局浮层/过渡；禁止继续无边界增加全局样式文件 |
| 图标 | lucide-vue-next | 新代码统一使用该库；迁移旧图标时逐步处理 |
| 通知反馈 | vue-sonner / 项目既有封装 | 不新增第二套 Toast/通知机制 |
| 状态与路由 | Pinia / Vue Router | 不在组件内另造全局状态或路由体系 |

## 4. 按钮治理

### 目标

新代码的基础按钮优先使用 TDesign Button，并通过项目级轻量封装/统一 props 与 token 保持语义和尺寸一致。若项目已有统一 Button wrapper，先复用它；禁止再增加第三套按钮组件。

### 现有入口（待逐调用点迁移）

- TDesign：`.t-button`
- 项目类：`.ui-btn` 及其修饰类
- 弹窗类：`.modal-btn-primary`、`.modal-btn-ghost`、`.modal-btn-danger`
- 其他历史类：例如 `.glow-btn`、图标按钮类

不得仅凭类名相似就批量替换。先建立每个入口的调用清单，确认原生 button、TDesign Button、表单提交、图标按钮、弹窗 footer 等语义差异，再按页面迁移。

统一覆盖：主/次/危险/文字/图标语义、尺寸、圆角、字重、图标间距、hover、active、focus-visible、disabled、loading、移动端触控尺寸。

## 5. 弹窗治理

- 先区分 vue-final-modal 项目 Modal 与 TDesign Dialog 的实际使用场景。
- 业务表单/复杂业务弹窗优先复用项目 Modal 封装；轻量确认/提示可使用 TDesign Dialog（以项目已有调用约定为准）。
- 不允许为同一个弹窗同时叠加两套定位、遮罩、滚动锁定或键盘处理逻辑。
- 桌面端业务 Modal 应居中；移动端可采用底部抽屉，但不能把移动规则无差别套到 TDesign Dialog。
- 公共行为统一：z-index、遮罩、宽高上限、内部滚动、Esc/关闭、焦点管理、滚动锁定、键盘弹起、安全区。
- 修改全局弹窗规则前必须搜索 Modal/Dialog 组件及全部调用点，覆盖桌面和移动端回归。

## 6. CSS 分层规则

建议按职责收敛，而不是简单按文件名判断：

1. Tokens：语义变量定义唯一值；主题只切换变量值。
2. Tailwind：布局与响应式工具类。
3. TDesign overrides：只处理 TDesign 必要的主题适配，避免与组件类重复定义。
4. Component styles：组件自身样式，优先 scoped。
5. Modal/overlay styles：只管理全局浮层定位、层级和跨组件过渡。
6. Legacy compatibility：历史类的临时兼容区，记录调用数、负责人/迁移目标；迁移完成后删除。

约束：
- 禁止新增重复的全局按钮/输入框/卡片样式体系。
- 禁止用全局 `button` 等宽泛选择器修单页。
- `!important` 仅用于第三方组件确实无法通过正常优先级覆盖的场景，并写明原因；不允许层层叠加。
- 同一选择器不得在多个全局文件反复定义不同的核心属性，确需覆盖时必须有清楚的层级和注释。
- 文件注释必须与 `main.ts` 的真实导入顺序一致。
- 不直接删除疑似旧 CSS；先搜索模板、脚本动态 class、字符串拼接和第三方渲染节点的使用情况。

## 7. 主题治理

- 主题状态以 `src/utils/theme.ts` 为唯一状态入口。
- 主题 class 与 tokens 必须一一对应；组件只消费语义变量，不自行判断系统主题。
- 不允许应用主题与 `prefers-color-scheme` 各自决定不同 UI 的颜色。
- normal、eye、dark 三种主题均需检查页面、TDesign 控件、Modal、Dialog、Toast、下拉浮层、图表和固定导航。

## 8. 分阶段迁移

### Phase 0：基线盘点（先做）

- 读取实际 CSS 导入顺序。
- 统计每个按钮类、输入类、卡片类、弹窗类的定义位置和调用位置。
- 统计 TDesign 组件和自定义组件使用点。
- 识别重复选择器、重复属性、冲突的 `!important`。
- 输出“保留/合并/迁移/删除候选”清单；删除候选必须有零调用证据。

### Phase 1：先修确定性问题

- 修复重复 HTML 属性等模板问题。
- 修复主题状态与主题色来源不一致。
- 清理 Observer、事件监听器、定时器等生命周期资源。
- 不借机改变业务逻辑和 API。

### Phase 2：建立统一控件入口

- 确认或建立单一项目 Button wrapper（先检查现有组件，避免重复造轮子）。
- 统一表单控件常用尺寸与状态。
- Modal/Dialog 统一使用边界明确的封装。
- 先迁移高频公共组件，再迁移页面。

### Phase 3：收敛 CSS

- 将重复规则迁入明确职责文件。
- 每迁移一组类，搜索调用点并回归三主题、桌面/移动端。
- 旧类保留兼容，调用数归零后再删除。
- 最后再评估是否能合并或移除 CSS 文件。

### Phase 4：依赖清理

- 对 package.json 每项依赖搜索 import、动态 import、插件配置、脚本和组件注册。
- 只有确认无使用后才提出删除；一次只清理可验证的一组依赖。
- 不为追求“少依赖”替换成熟且正在使用的库。

## 9. 验收标准

- 同一语义按钮在不同页面外观和交互一致。
- 桌面 Modal 居中，移动端布局符合既定策略；Dialog 不被 Modal 规则误伤。
- 三种主题在基础控件、浮层、通知、导航上保持一致。
- 全局 CSS 每个职责有清晰归属，导入顺序和注释一致。
- 没有未经评估的全局选择器或新增平行组件体系。
- 执行并记录 `npm run typecheck`、`npm run test`、`npm run check:design-tokens`、`npm run build`；另行进行真实浏览器桌面/移动视觉验收。
- 只报告实际执行的验证，不将静态审查描述为视觉验收。

## 10. 本规范不授权的操作

本规范本身不授权删除依赖、重写页面、修改后端 API/业务语义、变更生产数据或部署。任何大范围迁移均需基于调用清单和可回滚的小批次 diff。
