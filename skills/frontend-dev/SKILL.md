# tg-sender 前端开发技能

本技能只服务于本仓库 `web/`，不是通用 Vue 模板。**当前仓库实现、产品行为和用户明确要求优先于本文一般建议。** 代码与本文冲突时，先核实现行约定，不得机械覆盖。

## 1. 项目基线：每次任务先核对

当前已知技术栈（以当前分支为准）：Vue 3、TypeScript、Vite、Vue Router 4、Pinia、TDesign Vue Next、lucide-vue-next、vue-final-modal、vue-sonner、Tailwind CSS 4、Vitest、vue-tsc。

关键位置：
- `web/package.json`：依赖与脚本
- `web/src/main.ts`：插件按需注册、全局 CSS 导入顺序
- `web/src/router/`、`web/src/views/`、`web/src/components/`
- `web/src/styles/`：令牌、主题、UI 基类、TDesign 覆盖和弹窗样式
- `web/src/utils/theme.ts`：主题状态
- `skills/frontend-review/SKILL.md`：全面审查流程

任务开始先读取与本次修改有关的文件及调用方。不要假定历史路径、组件、脚本、CSS 类名仍然有效。

## 2. 不可违反的项目约束

1. 不引入 Element Plus、Ant Design、Naive UI 等未采用的 UI 库；不照搬其组件标签、API 或 CSS 类名。
2. 不擅自替换 TDesign、Vue Final Modal、Pinia、路由、请求封装或图标体系。
3. 未经明确同意不新增 npm 依赖。
4. 不改变后端 API 契约、字段、枚举、状态码、权限、任务语义或持久化格式来迁就 UI。
5. 不删除业务能力、兼容逻辑或用户数据处理来简化界面。
6. 不把通用审美偏好（例如禁止渐变、一律纯色或统一圆角）凌驾于项目现有视觉基线和用户要求。
7. 不用大范围全局选择器、堆叠 `!important` 或复制 CSS 快速修单页。
8. 静态阅读不能冒充浏览器实测；未执行的测试和部署不能声称通过。

## 3. UI 体系：先理解现状，再修根因

项目历史上存在多层 CSS 和多种按钮入口，例如 TDesign `.t-button`、项目 `.ui-btn`、图标按钮、弹窗专用按钮类，以及多个全局 CSS 层。它们是需要梳理的现状，不是继续新增平行体系的理由。

修改 UI 前必须：
1. 从 `main.ts` 确认真实 CSS 导入顺序。
2. 检查 tokens、ui-kit、TDesign 覆盖、modal-system 和 scoped 样式的层叠关系。
3. 搜索目标 class/component 的全部调用点，区分公共约定、历史遗留和页面局部实现。
4. 检查同类页面当前用法，优先复用维护中的实现。
5. 若规则冲突，先确认真实生效规则和影响范围，再提出最小统一方案。不能仅凭 CSS 文件注释声称某文件是唯一真相源。

### 按钮与控件

- 优先复用已有按钮组件/类和 TDesign Button，不另造按钮体系。
- 主、次、危险、文字、图标操作按语义区分；同语义操作保持尺寸、颜色、圆角、字重、图标间距和状态反馈一致。
- 检查 hover、active、focus-visible、disabled、loading 和防重复点击。
- 图标按钮必须有可访问名称；装饰图标避免被读屏重复朗读。
- 非提交按钮明确 `type="button"`，表单提交按钮明确 `type="submit"`。
- 修改公共样式前搜索全部调用点并评估回归风险。

### 表单、表格和反馈

- 复用已注册的 TDesign 组件及项目封装；新增组件前检查 `main.ts` 按需注册。
- 表单覆盖标签、校验、提交中、禁用、错误提示、防重复提交和成功后刷新。
- 表格考虑加载、空、错误、分页、长文本、窄屏和行操作。
- 使用项目已有 Toast/通知机制，不另造提示系统。

## 4. 桌面端与移动端

涉及布局、导航、弹窗、抽屉、表格或表单时，必须同时考虑双端。

**桌面端：**
- 遵循现有 AppShell、侧栏、顶部栏和内容区结构。
- 桌面模态框按项目当前规则居中；检查遮罩、层级、宽度/高度上限、内部滚动和 footer。
- 检查父级 transform/overflow、固定头部等是否影响定位。
- 工具栏、表格、分页和操作按钮应对齐，避免同一行控件高低不齐。

**移动端：**
- 遵循项目现有导航和断点，不另造一套。
- 自定义 Modal 当前可能采用底部抽屉策略；不要把该策略无差别套用到 TDesign Dialog 或其他浮层。
- 检查安全区、软键盘、VisualViewport、底部导航遮挡、固定操作栏、触控尺寸、横向溢出和滚动锁定。
- 群链接、消息、账号和任务长文本应能换行/截断并可查看完整内容。
- 小屏按钮不得挤压、溢出或被固定区域遮挡。

## 5. 主题和样式令牌

项目主题工具当前包含 normal、eye、dark 三态；具体 class/token 以 `src/utils/theme.ts` 和主题 CSS 为准。

- 新增颜色、边框、阴影、间距、字号、圆角前先查已有 token。
- 检查三种主题下的文字对比、边框、输入状态、弹窗、Toast 和浮层。
- 应用主题以项目主题状态为准，不可仅用操作系统 prefers-color-scheme 覆盖用户选择。
- 避免页面硬编码颜色破坏主题切换。
- 不凭个人审美重做整套主题；视觉改版应保留业务信息架构。

## 6. Vue、TypeScript、状态与 API

- 新代码优先 Composition API + `<script setup lang="ts">`；修改旧组件不为风格统一而无关重写。
- Props、Emits、API 入参/出参和复杂状态应有准确类型；不以 `any` 或双重断言掩盖错误。
- 派生状态用 computed；模板避免复杂逻辑；动态列表使用稳定 key。
- Pinia 解构 state 时保持响应性（必要时使用 `storeToRefs`），避免组件与 Store 保存两份状态真相。
- 复用项目 API 封装、拦截器、错误处理和类型；不在页面另造请求层。
- 清理 Observer、事件监听、定时器、订阅和可取消请求；处理请求竞态、重复提交、卸载后更新和错误吞没。
- 仅在有清晰复用边界时抽组件/composable，不为拆分而拆分。

## 7. 修改与验证流程

1. 确认当前分支、最新提交、目标文件及调用方。
2. 还原组件、样式、路由、API、主题和数据流的真实依赖。
3. 区分公共根因与页面特例。
4. 实施最小但完整的修复，保留业务行为，不顺手重构无关模块。
5. 检查 diff：重复 HTML 属性（尤其重复 class）、无用 import、意外删除、API/权限变化、调试代码和敏感信息。
6. 按当前 `web/package.json` 实际脚本执行验证。当前已知脚本：
   - `npm run typecheck`
   - `npm run test`
   - `npm run check:design-tokens`
   - `npm run build`
7. 逐项记录通过、失败、未执行及原因。代码验证和浏览器视觉验收分开报告。

用户要求全面处理时，尽量按模块一次完成，不要只零散修一个小点。无法运行浏览器时，明确标注未进行真实视觉验收。

## 8. 审查范围

配合 `skills/frontend-review/SKILL.md`，覆盖实际存在的工作区、群发、群组库、账号/会话、任务、设置、管理端、登录注册页面，以及 AppShell、导航、Modal、按钮、表单、Toast、表格和移动组件。

检查视觉一致性、桌面弹窗居中、控件对齐、图标尺寸、间距、字号、主题状态、空/加载/错误态、键盘/焦点/遮罩/Esc、aria 名称、横向溢出和固定元素遮挡。

## 9. 业务与环境安全

- 群组、账号、会话、消息、任务的数据筛选、去重、导入、发送、权限和调度逻辑均属核心业务；样式修改不得改变这些行为。
- 涉及群发/自动化时保留既有频率限制、账号状态、权限和失败处理，不得为 UI 顺畅绕过后端限制。
- 不输出或提交 session、API token、Cookie、密码、真实账号文件或 .env。
- 默认只修改仓库，不连接生产服务器、不操作生产数据库、不部署。部署须有明确要求及实际授权。

## 10. 完成汇报

简明说明修改文件、根因和用户影响、实际执行的命令及结果、未实测场景、Git 分支与提交 SHA、是否部署。禁止使用超出验证范围的“全部正常”“彻底解决”等表述。
