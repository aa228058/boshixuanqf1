# frontend-dev — 前端开发规范与 Vue 3 编码约束

> 上游来源：[doccker/cc-use-exp — skills/frontend-dev](https://github.com/doccker/cc-use-exp/tree/main/skills/frontend-dev)
> 上游作者/维护者：doccker。此技能基于上游 frontend-dev v3.0，保留核心规范，并增加本项目适配约束。
> 上游仓库当前标注为停止维护，后续维护请优先检查其迁移目标及本项目实际依赖，不要假定上游仍持续更新。

## 1. 本项目技术栈与优先级

本仓库前端位于 `web/`，使用 Vue 3、TypeScript、Vite、Vue Router、Pinia、TDesign Vue Next、Lucide Vue、Vitest。

**本项目优先级高于上游通用示例：**
- UI 组件库使用项目已安装的 **TDesign Vue Next**，不得照搬 Element Plus、Ant Design 的组件标签、API 或样式类名。
- 图标使用项目现有 Lucide Vue 方案；不得混用多套图标库或用 emoji 代替功能图标。
- 路由、状态、API 请求、权限和布局必须遵循仓库现有实现，不擅自引入新的架构或依赖。
- 先阅读现有公共组件、设计令牌和 `web/src/styles/ui-kit.css`，优先复用。

## 2. UI 风格约束

### 严格避免
- 蓝紫霓虹渐变、发光描边、玻璃拟态、赛博/暗黑科技风。
- 大面积渐变、无意义装饰几何图形、过度阴影和装饰性动效。
- UI 文案使用 emoji（除非产品明确要求）。
- 同一页面混用多套按钮、表单、图标或弹窗视觉语言。

### 后台系统默认风格
- 以现有 TDesign 主题和项目设计系统为准，不重置或随意改写全局主题。
- 黑白灰为主，使用项目既定主色作为少量强调。
- 信息密度适中；表格、筛选、分页、表单优先使用现有标准组件。
- 动效克制，只保留必要的 hover、focus、loading 和状态过渡。
- 相同语义的按钮、标签、输入框、卡片、表格、分页和状态提示必须保持一致。

## 3. Vue 3 编码规范

- 新增/修改 Vue 组件优先使用 Composition API 与 `<script setup lang="ts">`。
- Props、Emits、API 请求体和响应数据必须有明确 TypeScript 类型。
- 组件文件使用 PascalCase；Composable 使用 `useXxx.ts`；Store 使用 `useXxxStore.ts`。
- 组件内逻辑按导入、Props/Emits、Store/Composable、响应式状态、计算属性、生命周期、方法组织。
- 使用 `computed` 表达派生状态；避免在模板中堆复杂表达式或重复计算。
- 列表必须提供稳定唯一的 `:key`；不要用不稳定数组索引充当动态列表身份。
- 生命周期注册的事件、观察器、定时器和请求应在适当时机清理或取消。
- 避免超大组件；仅在存在清晰复用边界或职责边界时拆分，不为拆分而拆分。

## 4. Pinia 与响应式状态

- Store 按业务域组织，避免一个全局 Store 承担所有业务。
- 组合式 Store 应清晰区分 State、Getters（computed）和 Actions。
- 从 Store 解构响应式状态时使用 `storeToRefs`；Actions 可直接解构。
- 大型只读数据可评估 `shallowRef`；不要未经测量就复杂化响应式方案。
- 不要在组件中复制一份 Store 状态造成双向不同步。

## 5. TypeScript 与 API 类型安全

- 默认使用 TypeScript；禁止以大范围 `any`、双重断言或随意类型断言绕过错误。
- API 响应、分页结构、表单模型、请求参数和组件事件应复用统一类型。
- 通用类型优先放在项目现有公共 types 目录，避免多文件重复定义。
- API 工具函数应提供泛型或明确返回类型；调用处按真实响应结构声明类型。
- UI 表单字段必须完整映射到提交请求体；新增/修改表单字段时检查请求构造，避免“界面能选但提交未传”。
- 不得擅自改变后端 API 字段、枚举、状态码或兼容行为。

## 6. 交互状态必须完整

涉及数据加载、表单提交、批量操作和异步任务时，检查：
- loading：加载中反馈，避免重复触发。
- empty：空数据状态与下一步操作提示。
- error：失败原因、可恢复操作或重试入口。
- disabled：不可操作时给出正确禁用状态。
- submitting：提交期间防止重复提交，并在完成/失败后正确恢复。
- success：成功反馈与数据刷新/状态同步。

不要静默忽略非成功响应或网络异常。错误提示遵循项目现有统一通知机制，不要每个页面另造提示系统。

## 7. API 与数据流

- 使用项目现有 API 封装、拦截器和错误处理约定，不在组件中散落重复的 fetch/axios 封装。
- 对请求异常、非成功业务响应、空响应和字段缺失做合理处理。
- 检查请求竞态、重复请求、组件卸载后更新状态等问题。
- 用户在 UI 中输入或选择的字段必须按业务规则完整传入 API。
- 前端校验应与后端约束保持一致，但前端校验不能替代后端校验。
- 不在前端硬编码密钥、令牌或服务端私密配置。

## 8. 样式管理

- 共享颜色、间距、字号、圆角、阴影和组件样式优先使用项目现有设计令牌。
- 全局/共享样式放在项目现有 styles 目录；组件私有样式使用 scoped。
- 不新增平行设计系统，不通过大量 `!important` 或高优先级选择器覆盖公共组件。
- 修改公共按钮、弹窗、表格或表单样式时，必须检查其所有调用页面，防止全局回归。
- 避免在 Vue SFC 中堆积大段样式；可复用样式抽到公共样式文件。
- 不机械照搬上游“style 不超过固定行数”的阈值；以可维护性、复用边界和仓库既有规范为准。

## 9. 响应式与可访问性

- 每次涉及布局、弹窗、导航、表格或表单的改动，都同时考虑桌面端和移动端。
- 避免固定宽度导致窄屏横向溢出；检查长文本、长链接、超长列表和底部固定操作区。
- 弹窗需检查桌面端居中、最大高度、内部滚动、遮罩、Esc、焦点和层级；移动端遵循项目既有弹窗/抽屉策略。
- 图标按钮必须有可访问名称；表单字段必须有可见标签或等效关联。
- 键盘可达、焦点可见、语义化元素和合理 ARIA 状态不可退化。
- 不能仅靠颜色表达成功、失败、警告或选中状态。

## 10. 性能原则

- 先保证正确性，再基于真实瓶颈优化。
- 大列表在数据规模和交互场景确有需要时采用虚拟滚动或分页。
- 路由/重型组件可按需懒加载。
- 对搜索等高频请求使用合理防抖、取消或竞态保护。
- 不为了“性能优化”引入不必要依赖、缓存复杂度或难以验证的微优化。

## 11. 本项目前端审查流程

用户要求审查、排查或全面修复前端时，配合 `skills/frontend-review/SKILL.md` 执行。至少覆盖：
1. 阅读 package scripts、路由、布局、公共组件、全局样式和设计令牌。
2. 扫描全部页面与组件，按业务模块盘点，不只检查最近改动文件。
3. 检查按钮类型/样式、弹窗定位与滚动、表单状态、标签页/菜单语义、移动端溢出、图标可访问名称。
4. 先修公共组件和设计系统根因，再处理页面特例。
5. 分别执行实际存在的 typecheck、test、design-token check、build 命令；逐项报告真实结果。
6. 没有浏览器实测就明确说明，不能把静态代码检查说成 UI 实测。

问题等级：P0 安全/数据丢失/核心不可用；P1 核心流程故障；P2 明显视觉、交互或可访问性问题；P3 低风险瑕疵。

## 12. 常用验证命令

先确认 `web/package.json` 当前脚本，再执行：
```bash
cd web
npm run typecheck
npm run test
npm run check:design-tokens
npm run build
```
任何命令未执行、失败或被环境阻断，都必须如实记录，不得声称全部通过。
